About WebRTC and privacy

Shared-room messages travel directly between browsers over WebRTC data channels. Browsers use DTLS to encrypt data in transit, and room message text is not relayed through the OpenChat server. Room counts show current signaling connections, not a global directory of OpenChat servers.

The server still handles room membership and relays peer connection offers and answers. It also receives display names, profile pictures, and invite codes. Peer identity is not cryptographically verified; a malicious or compromised signaling server could interfere with connection setup. OpenChat has not had an independent security review.

Rooms connect each participant directly to every other participant, with no fixed participant cap. The number of peer connections grows quickly as rooms grow, and large rooms may overwhelm devices or networks. The server operator may configure STUN or TURN servers; without them, some network setups cannot connect. TURN credentials are delivered to browsers and should be temporary. Shared-room peer connections retry ICE negotiation after a failure. WebRTC can disclose network addresses to other participants and infrastructure involved in connection setup.

Messages show direct peer delivery acknowledgements and can be retried for peers that have not confirmed receipt. Search and replies use only the conversation history cached in this browser. Direct messages also use WebRTC; their offer and answer must be copied between contacts manually, and friend codes should be compared using a separate trusted channel.

Voice and video are not implemented. DTLS-SRTP transport encryption alone does not provide authenticated end-to-end identity; a key-verification protocol and independent security review would be needed before making that claim.

Messages cached by this browser are stored in local storage without encryption. For sensitive conversations, use an independently reviewed messaging application.
